## 헥사고날에 대한 사실과 오해       

### 헥사곤을 부르는 여러가지 이름
- 헥사곤
- 애플리케이션
- ...

### 포트
- 애플리케이션이 외부 세계외 **의도** 를 가지고 상호작용하는 아이디어를 캡처한 것
- 의도를 가지고 만들어짐

### 인터페이스
- Lollipop: Provided Interface
    - 애플리케이션이 제공하는 인터페이스이므로 다양한 액터들이 갖다 쓸 수 있음
- Socket: Required Interface
    - 애플리케이션이 가지고 있지는 않지만 필요로 하는 인터페이스. 외부에서 제공하는 기능들
    - 해당 인터페이스에 연결하는 액터를 Secondary Actor 라고도 함

### 어댑터
- 애플리케이션 포트를 액터가 직접 연결할 수 없는경우 이용


### 헥사고날 아키텍처의 비대칭성
- 애플리케이션이 제공하는 기능을 사용하는 액터와 어댑터
    - primary actor
- 애플리케이션이 동작하는데 필요한 기능을 제공하는 액터와 어댑터
    - secondary actor

### 오해: 애플리케이션 내부에 도메인 계층을 만들어야 한다.
- 트랜잭션 스크립트 패턴을 이용해도 되고 스파게티 코드로 만들어도 됨
- 클린 아키텍처와 구분할 것

### 오해: 헥사고날 아키텍처 패키지 구조를 따라야 함
- 헥사고날 아키텍처가 요구하는 패키지구조는 없음
    - 애플리케이션과 어댑터 패키지를 분리하는 정도면 됨
    - 포트를 구분된 패키지에 두면 좋음 

### 오해: 꼭 포트 뒤에 UseCase 라는 접미사를 사용함
- 포트의 의도를 담은 이름을 사용하면 된다.
- For + ~ing 를 쓰는 네이밍이 있는데 필수는 아님

### 오해: 애플리케이션에는 도메인 모델만 넣고 JPA 엔티티등은 어댑터에 둔다
- 애플리케이션 코드와 포트 인터페이스가 외부 기술에만 의존않으면 된다 (요구사항)

### **팩트**: 헥사고날 아키텍처의 요구사항
- 애플리케이션은 모든 외부와의 상호작용을 위해 provided interface 와 required interface 를 정의한다.
- 애플리케이션과 상호작용 하는 액터는 런타임에 구성되어야 한다.
- 애플리케이션은 액터에 대한 코드 의존성을 가지면 안된다.

- Spring 의 DI 와 사실 유사한 철학

- 액터는 정의된 포트를 통해서만 연결해야 함
- 포트의 인터페이스는 기술 의존성을 가지지 않는다
